## Design Specificity Verdict

**LLM assessment**: Mostly authored, not generic — but unevenly finished. The catalog cards (`/games`), the leaderboard (felt header, gold/silver `.rank-medal`, mono scores, drawn trophy), and the booking-code reveal (gold border, 2rem tracked mono code) are genuinely specific to a board-game world — no generic admin tool produces these unprompted. But `ManageBookingView.vue`'s found-booking block and `EventAdminDetailView.vue`'s "Prenotazioni attive" / "Risultati inseriti" lists render as unstyled plain-text rows with a raw English enum (`stato: active`) — could be pasted into any CRUD app unchanged. Specificity is real where designed, absent where the pass didn't reach.

**Deterministic scan**: `detect.mjs --json frontend/src` found 1 finding: `codex-grid-background` on `frontend/src/app.css:85` (a subtle dot-grid background on `body`, `20px` cell, 4% opacity). **Likely false positive** — the file's own header frames the whole stylesheet as a single committed "dado & pedina su tavolo in feltro" system, and this reads as felt/table texture, not generated-UI grid slop.

Live-page injection (via the browser overlay, run on `/`, `/events/1`, `/admin/events`, `/games`) surfaced two more rules the static scan missed: `gpt-thin-border-wide-shadow` (1px border + 16px shadow blur) on the `.event-games`/`.event-list`/`.game-grid` `<li>` cards on every page, and `flat-type-hierarchy` (body font sizes cluster 12.8–15.3px, a 2.0:1 ratio) on `/` and `/admin/events`. `cream-palette` also fired on all 4 pages — also a **likely false positive**, since `#faf6ec` cardboard-on-felt is DESIGN.md's explicit, deliberate palette, not an unintentional default. The border/shadow and flat-hierarchy findings are worth a second look even though the palette/grid ones aren't: they're independent of the felt/card theme and point at real type-scale compression.

**Visual overlays**: injection succeeded during evidence gathering, but the sub-agent stopped its local `live-server.mjs` session before finishing, so there's no live overlay left open in a browser tab to view — the findings above are the captured console output, not something currently visible.

## Overall Impression

The felt-and-cardboard identity is real and it shows up exactly where it should — the leaderboard, the booking-code card, the catalog shelf. But the app currently has one event and one game, and at that scale two structural problems are highly visible: `auto-fill` grids leave lone cards floating in oversized void, and two admin list views (bookings, results) never got the card treatment the rest of the app has. The single biggest opportunity is closing that gap before more content exists to hide it — plus giving the booking and leaderboard flows back the one piece of context (which game) they currently drop.

## What's Working

1. **Booking-code card** (`.booking-code-card`) — gold border reserved exactly per DESIGN.md's "conserva questo" rule, at exactly the moment a participant needs to remember something. The one component where the design system's stated intent and the shipped UI match perfectly.
2. **Leaderboard table** — felt-green header, medal badges, mono tabular scores, hand-drawn trophy badge (never an emoji). A fully realized, non-generic execution of the "german-style board game, not poker" north star from DESIGN.md.
3. **Catalog cards** (`/games`) — reads as a shelf of boxes, not a data table; genuinely fulfills the stated creative direction.

## Priority Issues

**[P1] `auto-fill` grids leave dead space with few items.** `frontend/src/app.css` lines 635, 766, 823, 872 (`.game-grid`, `.event-list`, `.event-grid`, `.event-games`) use `grid-template-columns: repeat(auto-fill, minmax(Xpx, Ypx))`. With the app's actual current content (one event, one game), `auto-fill` reserves empty implicit tracks — a single card floats in a large dark-green void on the event page and a large beige void on every list. This directly undercuts the "table"/"shelf" metaphor at the exact content volume a small association will realistically have for a while.
**Fix**: switch to `auto-fit`, or cap/center the grid container when the item count is low.
**Suggested command**: `/impeccable layout`

**[P1] Booking form and leaderboard drop the game name.** Confirmed in code: `EventDetailView.vue`'s booking form has no heading referencing the selected game; `GameLeaderboardView.vue:52` hardcodes `<h1>Classifica</h1>` with no game name. This forces recall exactly at the two highest-stakes moments (committing to book, reading history) — worst if a participant gets interrupted mid-flow and returns.
**Fix**: surface the game name in both headings.
**Suggested command**: `/impeccable clarify`

**[P2] Plain-text leaks break the design system.** `ManageBookingView.vue` (found-booking block, ~L112-118) prints `Prenotazione per {name} — {game} — stato: {status}` unstyled with a raw English enum; `EventAdminDetailView.vue`'s "Prenotazioni attive" / "Risultati inseriti" lists do the same. Every other list in the app uses the card-surface + mono-data pattern; these two don't.
**Fix**: bring both onto the existing card-surface/mono pattern, and translate/label the status enum instead of printing it raw.
**Suggested command**: `/impeccable polish`

**[P2] Flat type hierarchy on public/admin list pages.** Detector-confirmed on `/` and `/admin/events`: body text sizes cluster in a 12.8–15.3px band (2.0:1 ratio), which reads as everything-the-same-weight rather than a clear primary/secondary split — consistent with Assessment A's read of the aesthetic score (3/4, "undercut by dead grid space" and flat weighting together).
**Fix**: widen the type scale between page titles, card titles, and metadata text.
**Suggested command**: `/impeccable typeset`

**[P2] No confirmation on destructive actions.** "Rimuovi" (admin user row, player row), "Elimina gioco," and "Annulla prenotazione" all fire on a single click with no undo.
**Fix**: add a confirm step (inline or modal) before these fire.
**Suggested command**: `/impeccable harden`

**[P3] Thin-border-plus-wide-shadow card treatment.** Detector-confirmed on the `<li>` cards across `/`, `/events/1`, `/admin/events`, `/games`: 1px border combined with a 16px shadow blur is a pattern the detector associates with generic AI-generated card styling. This is DESIGN.md's own committed `--shadow-card`/`--shadow-lift` vocabulary, so it's not necessarily wrong — but worth a deliberate look, since it's the one deterministic signal that showed up identically on every page rather than being page-specific.
**Suggested command**: `/impeccable audit`

## Persona Red Flags

**Casey (distracted mobile booker)**: Scrolls past the felt table into an anonymous booking form with nothing telling her which game she's booking — if she's interrupted and comes back, she has to scroll back up to check. The booking code (`A8FWZKCN`) has no copy-to-clipboard affordance, so she has to manually retype or screenshot it standing at the table.

**Alex (admin power user)**: No search or filter on the catalog or event list, and no bulk actions on bookings/results — both admin list views render as plain unstyled rows with no click-through. Settings' three API-key fields (BGG, YouTube, Search) give no indication of what enabling each one unlocks, forcing trial-and-error before the admin will risk pasting in a real key.

**Sam (accessibility)**: The focus outline reuses the same warm-red accent (`#9c2b2b`) as `.btn-danger` and error backgrounds — a keyboard user tabbing through `/manage-booking` can't distinguish "this is focused" from "this is an error" by color alone.

## Minor Observations
- Error copy ("prenotazione non trovata") is lowercase, terse, and offers no next step.
- `/manage-booking`'s code input isn't uppercased/monospaced to match how the code is displayed elsewhere.
- The score-save confirmation ("Punteggio salvato.") is purely functional — no warmth at the actual emotional climax of the night (who won); the trophy badge only appears if the participant separately navigates to the leaderboard, which nothing on the booking-management screen links to.
- A finding initially read as a possible security gap — `/games/:id` showing edit/delete controls on what's meant to be a public participant-facing route — turned out to be a false positive from testing inside an already-authenticated browser tab: `GameDetailView.vue` correctly gates every admin control behind `v-if="auth.user"`, and the backend (`internal/httpapi/router.go`) requires auth on every mutating `/api/games/*` route. No action needed, but worth knowing for future audits: test this route in a private/incognito context.
